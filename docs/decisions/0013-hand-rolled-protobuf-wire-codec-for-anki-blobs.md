# Hand-Rolled Protobuf Wire Codec for Anki Schema-18 Blobs

## Context and Problem Statement

Anki's modern collection schema (18) stores notetype, field, template, deck, and deck-preset configuration as protobuf-encoded blobs, and package v3 uses protobuf for the `meta` file and the media manifest. Supporting the modern format (ADR-0015) requires encoding and decoding these messages. Anki's `.proto` definitions are AGPL-3.0; srs-converter is MIT. Vendoring the proto files, or shipping code generated from them, would put AGPL-derived artifacts inside an MIT package.

## Decision Drivers

- License hygiene: no AGPL text or codegen output may end up in the published package.
- Dependency budget: the library currently has four runtime deps; a protobuf runtime plus codegen toolchain is a heavy add for ~10 small messages.
- Fidelity: blobs contain opaque areas (`other = 255`, add-on data) and Anki adds fields over time; round-trips must not drop bytes we do not model.
- The protobuf wire format is small, stable, and independently documented (<https://protobuf.dev/programming-guides/encoding/>); field numbers and types are interoperability facts, not copyrightable expression.

## Considered Options

1. Hand-rolled minimal wire-format codec for exactly the messages we need
2. Author our own `.proto` subset and generate TypeScript with protobuf-es
3. Vendor Anki's `.proto` files (or their generated code)

## Decision Outcome

Chosen option 1: a small hand-written encoder/decoder over the protobuf wire format (varint, fixed32/64, length-delimited), covering only the messages in the pinned wire spec (`docs/formats/anki.md`, "Pinned wire-format spec"): `PackageMetadata`, `MediaEntries`/`MediaEntry`, `Notetype.Config` (+ `CardRequirement`), `Notetype.Field.Config`, `Notetype.Template.Config`, `Deck.Common`, `Deck.KindContainer`/`Normal`/`Filtered` (+ `DayLimit`, `SearchTerm`), and `DeckConfig.Config`.

**Codec invariants:**

- **Unknown-field passthrough.** Decoding retains the raw bytes of any field number the codec does not model; encoding re-emits them. This covers Anki's `other = 255` opaque blobs, add-on data, and fields added by future Anki versions. Same-schema round trips must be semantically lossless even for unmodeled data.
- **Facts only, no copied text.** The codec is written against the field tables in `docs/formats/anki.md` (facts extracted from the pinned Anki source), never by copying proto text or generated code into the repo.
- **Proto3 semantics.** Default values are omitted on encode (except inside `oneof`), unknown enum values are preserved as numbers, `optional` (explicit-presence) fields are tracked distinctly from absent defaults.

### Consequences

- Good, because zero new runtime dependencies and no AGPL-derived code in the package.
- Good, because unknown-field passthrough gives forward compatibility a naive codegen setup would not.
- Bad, because we own the maintenance: when Anki adds fields we care about, the spec doc must be re-pinned and the codec extended by hand.
- Neutral, because re-encoding is semantically but not necessarily byte-identical (field order/varint canonicalization); Anki's importer does not require byte identity.

### Confirmation

Decode→encode→decode round-trip tests over real fixtures generated by Anki (see fixture-corpus story), including a fixture with add-on data in `other`; differential test that a legacy and a modern export of the same collection parse to equivalent entities.
