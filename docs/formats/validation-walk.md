# Validation Walk — Source Formats → USF

Part of Story 5.0.1 / spec §12.5. Entity-by-entity, column-by-column walk of the four researched formats through **import into USF**, recording each source construct's destination. Export folds are noted only where the spec defines them.

```text
Date:       2026-07-11
Spec:       docs/spec/universal-srs-format.md — 1.0.0-draft.2
Dossiers:   anki.md, mnemosyne.md, supermemo.md, mochi.md (2026-07-10/11 state)
Status:     MUST be re-run against the final 1.0 text before acceptance (spec §12.5, Appendix A #8)
Findings:   #1–#6 resolved into draft.2 on 2026-07-12; rows updated in place
```

**A construct without a destination row is a spec bug, not an implementation choice** (spec §12.5). Constructs for which no destination could be determined from the spec are collected in [Findings](#findings) — destinations were **not** invented for them.

Legend for the **Destination** column:

- Named core field — with spec § reference in the Notes column.
- `extensions.<ns>` — namespaced extension (§11); the source's own exporter MUST restore it (restore obligation, §11).
- "dropped + reported" — loss surfaced through result reporting; silent loss is non-conforming (§3.2).
- "n/a" — nothing to carry: derivable cache, transport mechanics, or regenerated on export (reason given).
- **⚠** — §12 does not route this construct explicitly; the destination follows from the spec's general rules only (§3.3, §11). Maintainer eyeball requested.
- "Appendix A #5/#6/#7" — semantics the spec itself marks unconfirmed.

## Findings

### Constructs without a determinable destination — all six resolved into draft.2 (2026-07-12)

Original findings preserved; each carries its resolution, also reflected in the rows above.

1. **Anki deck-config identity.** §7.1 requires deterministic id derivation for every imported entity class ("`sourceKey` is defined per format in §12") and enumerates `deck-config` as an entity type; §12.1 defines sourceKeys only for notes, cards, decks, and note types. The id derivation for `dconf`/`deck_config` entities is undefined. (Row 1.3.) **Resolved:** §12.1 now derives deck configs from the 64-bit `dconf` id.
2. **Anki filtered-deck displacement fold.** §8.5 defers "filtered-deck displacement" to "fold rules in §12"; §12.1 routes `odid`/`odue` to `extensions.anki` but never states whether a displaced card's `deckId` names the filtered deck (`did`) or the origin deck (`odid`), nor how a filtered deck entity itself (`dyn` / `Deck.Filtered`) imports. (Rows 1.2, 1.6.) **Resolved:** filtered decks import as no deck entity (queries, not containers — ADR-0008); a displaced card's `deckId` is its home deck (`odid`).
3. **Mnemosyne per-card tags.** Tags attach to **cards** (`tags_for_card`); USF `tags` lives on the **note** (§8.4). No fold is defined for sibling cards of one fact carrying different tags. (Row 2.1.) **Resolved:** the note receives the union; exact per-card sets ride in `extensions.mnemosyne`; sibling disagreement is reported.
4. **Mochi trashed-card status.** §12.4 routes the `:trashed?` timestamp to `extensions.mochi` but assigns no core `status`; §8.5's enumeration (`active`/`suspended`/`archived`) contains no trash value and no fold is stated. (Row 4.4.) **Resolved:** `trashed?` folds to `archived` (reported); the trash timestamp in `extensions.mochi` restores the native state on round-trip.
5. **Mochi N-side content split.** Plain-card `:content` and template `:content` support N sides via `---`; USF templates are strictly two-sided (`question`/`answer`, §8.3). §12.4's "content-with-sides" names the shape but defines no side → question/answer rule for N > 2. (Rows 4.3, 4.4.) **Resolved:** side 1 → question, remaining sides concatenated in order → answer, reported when N > 2; note content stays verbatim.
6. **Mochi never-reviewed plain card.** §12.4 creates the `#main` `template` sibling "only when a main `:reviews` schedule exists". A plain (non-cloze, non-reverse) card with no reviews yet then yields a note with **zero** cards, contradicting the same sentence's "1–N universal cards". The destination of its schedulable unit is undetermined. (Row 4.4.) **Resolved:** the main `template` sibling is always created for non-cloze cards (empty history is legal); the `:reviews`-existence condition applies only to the grouped-cloze question (Appendix A #7).

### Observations (destination determinable, but only via general-rule fallback where a §12 rule seems intended)

- Synthesized note types (SuperMemo generic Q/A, row 3.2; Mochi plain cards, row 4.3) get fresh UUIDv7 ids per §7.1 — re-importing the same source therefore duplicates note types. §7.1's weak-identity report covers it, but a fixed synthetic sourceKey per format would close it. **Resolved 2026-07-12:** fixed synthetic sourceKeys (`supermemo:note-type:item-qa`, `mochi:note-type:plain`).
